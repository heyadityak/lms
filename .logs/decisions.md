# Decisions (ADR-lite)

Format: **D-NN — Title.** Decision. *Rationale.* (date, author). Append-only. To supersede an entry, add a new one and mark the old one "Superseded by D-xx".

- **D-01 — Single-tenant, one deployment per customer.** One DB per customer, no `tenant_id` columns. *Rationale:* white-label SMB/enterprise delivery. Isolation by infrastructure is simpler and safer than row-level multitenancy. (2026-11-19, architect)
- **D-02 — Ledger-based balances.** Append-only `leave_ledger_entries`, balance = SUM. No mutable balance columns. *Rationale:* auditability, idempotent accrual, and it fixes the original's lost-update/no-history design. Data volume is small, so SUM is fast with the `(user_id, leave_type_id, year)` index. (2026-11-19, architect)
- **D-03 — `database` driver for queue, cache, session.** No Redis. *Rationale:* minimal backing services (user requirement). Postgres handles the load of an LMS. Stateless processes are preserved. (2026-11-19, architect) *Superseded by D-23.*
- **D-04 — Calendar leave year, yearly grant on Jan 1.** No monthly accrual and no anniversary-based accrual in MVP. Requests may not span years. *Rationale:* simplest correct model. The original's anniversary-on-login update was not idempotent. Monthly accrual is Later (UC-H13). (2026-11-19, architect) *Amended by D-26 (configurable leave-year start month).*
- **D-05 — No Node/Vite build.** Blade + one hand-written CSS file driven by CSS custom properties. Auth screens written by hand (Laravel 12 starter kits require React/Vue/Livewire + Node). *Rationale:* fewer toolchains in the image and CI. Theming only needs CSS variables. (2026-11-19, architect)
- **D-06 — Overlap enforced twice:** app check + Postgres `EXCLUDE USING gist` on `daterange` for pending/approved. *Rationale:* race-proof without app locks alone. Needs `btree_gist`, which ships with the postgres image. (2026-11-19, architect)
- **D-07 — No `draft` status; `taken` is derived.** Statuses: pending, approved, rejected, cancelled. *Rationale:* drafts add UI/state without user value for a form this small. "Taken" = approved and started, computable. (2026-11-19, architect)
- **D-08 — Single-level approval in MVP.** Approver = active direct manager, else any HR admin. Nobody approves their own request. Multi-level and delegation are reserved module keys (`available=false`). *Rationale:* covers the original (HOD approves) and most SMBs. Approver is resolved at action time, so reorgs don't strand requests. (2026-11-19, architect)
- **D-09 — One multi-stage Dockerfile, two published images** (`app` from `app-prod`, `nginx`). The app image also runs worker, scheduler and one-off commands. Caches are built at container start, not build time. *Rationale:* 12-factor build/release/run. One artefact per role. Config is unknown at build time. (2026-11-19, architect) *Amended by D-27: the `app` image is FrankenPHP + Octane instead of php-fpm; still one Dockerfile, two published images.*
- **D-10 — CI tests use `setup-php` + Postgres 17 service, not the Docker image.** *Rationale:* faster, cached. Parity is kept on PHP minor + Postgres major. The image is still built (and fails the pipeline if broken) in `package`. (2026-11-19, architect) *Amended by D-25 (Redis service, OpenAPI lint, smoke test, multi-arch).*
- **D-11 — PHPUnit (not Pest), two suites.** Unit = plain `PHPUnit\Framework\TestCase`, no DB. Feature = Postgres `lms_test`. Never SQLite. *Rationale:* user choice. Postgres-only DDL must be exercised. (2026-11-19, architect)
- **D-12 — Users are never hard-deleted.** Deactivate instead. *Rationale:* audit/history. The original lost leave history when deleting employees. (2026-11-19, architect)
- **D-13 — Global leave-type quotas (no per-department override in MVP).** *Rationale:* the original set quotas per HOD/department. Overrides are Later (UC-H10) via an extra policy table without changing the ledger. (2026-11-19, architect)
- **D-14 — White-label config: env = defaults + licensed ceiling, `settings` table = admin overrides.** `effective = DB override ?? env default`. For modules: `enabled = licensed (MODULES_ENABLED env) ∧ available (registry) ∧ ¬disabled (settings)`, so an admin can switch off a licensed module but never switch on an unlicensed one. *Rationale:* 12-factor config per deployment, with the vendor controlling licensing at deploy time. Customers self-serve within it. Settings are data (in the DB), not config. (2026-11-19, architect)
- **D-15 — Branding assets on a Laravel disk (`BRANDING_DISK`), served through `/branding/{asset}`.** Local volume in dev, S3-compatible in prod. Never baked into the image. Content-hashed filenames. No SVG. *Rationale:* stateless containers. One code path for local and S3. Avoids SVG stored-XSS. (2026-11-19, architect) *Amended by D-24 (S3 disk everywhere incl. dev via RustFS; local disk only single-node).*
- **D-16 — Theming = CSS custom properties injected from validated hex settings.** No per-customer CSS builds and no arbitrary custom CSS in MVP. *Rationale:* zero build step, no injection surface. (2026-11-19, architect)
- **D-17 — Disabled module ⇒ 404 (not 403), hidden in UI, and inert in domain** (e.g. holidays off ⇒ holidays not excluded from day counts). *Rationale:* the feature appears absent rather than forbidden. Domain behaviour stays consistent with what the user can see. (2026-11-19, architect)
- **D-18 — Branding/modules administered by `hr_admin`; no separate customer-admin role in MVP.** *Rationale:* keeps 3 roles. Revisit if enterprises need IT-admin separation (open question). (2026-11-19, architect) *Superseded by D-29.*
- **D-19 — Sandwich rule off.** Weekends/holidays never count. *Rationale:* illegal or unpopular in many jurisdictions. Per-type flag is Later. (2026-11-19, architect)
- **D-20 — Keycloak 26 is the identity provider and RBAC authority; Sanctum removed.** One Keycloak per deployment (own container, own `keycloak` database on the same Postgres server, clustered in prod). Realm `lms`, realm roles `employee|manager|hr_admin`. Clients `lms-web` (confidential, OIDC auth code, used by Laravel Socialite + `socialiteproviders/keycloak`) and `lms-api-cli` (public, auth code + PKCE). Web: first login provisions the user by `users.keycloak_sub` (unique), every login syncs realm roles into `users.role` (a cache; Keycloak wins), session in Redis, logout is RP-initiated. API: Bearer JWT (RS256) validated by a custom guard against the realm JWKS cached in Redis, checking `iss`, `aud`/`azp` (allow-list `KEYCLOAK_ALLOWED_AUDIENCES`), `exp`/`nbf`. Removed from the app: passwords, `password_reset_tokens`, `personal_access_tokens`, forgot/reset/change password, account-created mail, token issue endpoints. HR still manages department, manager, joining date and deactivation in the app; roles are assigned in Keycloak only. Resource-level authorization (e.g. only the direct manager approves) stays in Laravel Policies. New composer deps: `laravel/socialite`, `socialiteproviders/keycloak`, `firebase/php-jwt`; drop `laravel/sanctum`. *Rationale:* enterprise customers federate their own directory (LDAP/AD, SAML, Entra ID) and get MFA/SSO/brute-force protection without app code; the Keycloak login theme can be white-labelled per customer. Policies keep the business rules that Keycloak roles cannot express. (2026-11-19, architect) *Partly superseded by D-22: the app may now create users and assign roles through the Keycloak Admin API; Keycloak remains the source of truth.*
- **D-21 — Contract-first REST API.** `docs/api/openapi.yaml` (OpenAPI 3.1) is the source of truth; guidelines in `docs/API_GUIDELINES.md`. URI versioning `/api/v1`, plural kebab-case nouns, state transitions as `POST …/{id}/approve|reject|cancel`, `/me` for the caller. Envelope `{data, meta, links}` via API Resources, snake_case, ISO-8601, public ids are ULIDs in a `public_id` column (bigint `id` never exposed). Errors are RFC 9457 `application/problem+json` with a stable `code`. Pagination `page[number]`/`page[size]` (max 100), `filter[...]`, `sort=`, `include=`. `Idempotency-Key` on `POST /leave-requests` (Redis, 24 h, replays the first response). `X-RateLimit-*` / `Retry-After` from Redis limiters. Every `/api/v1` route is behind the `api` module (404 when off). QA validates every API feature-test response against the spec (`osteel/openapi-httpfoundation-testing`, dev dep). Docs UI at `/api/docs` when `api` is enabled. *Rationale:* lets domain, QA and API consumers work in parallel against one contract; predictable machine-readable errors; safe client retries on flaky mobile networks. (2026-11-19, architect)
- **D-22 — In-app user administration through the Keycloak Admin REST API (supersedes D-20's "app never edits roles").** Keycloak stays the source of truth for identity and roles; the LMS writes to it, then mirrors locally. Auth: confidential service-account client `lms-admin` (client-credentials), service-account roles `realm-management`: `manage-users`, `view-users`, `query-users` only (never `realm-admin`); token cached in Redis until 30 s before expiry. Only `hr_admin` (a split-off `admin` role is a Later option). Operations: list/search, create (no password; `execute-actions-email` `UPDATE_PASSWORD`+`VERIFY_EMAIL`), update profile, enable/disable (disable also calls `logout` for the user), password-reset email, assign/revoke realm roles limited to the allow-list `employee|manager|hr_admin`; LMS attributes (department, manager, joining date) edited in the same form. Guardrails: no self-demotion/self-disable; last active `hr_admin` cannot be demoted/disabled (checked under a Redis lock); federated users (`federationLink` set, LDAP/AD) are read-only for profile fields, roles editable only if the provider accepts it. Keycloak 409 → `IDP_CONFLICT` (409), Keycloak unreachable/5xx → `IDP_UNAVAILABLE` (503), federated write → `IDP_READ_ONLY` (422). Consistency: Keycloak first (get id), then local insert with pre-provisioned `keycloak_sub` in a DB transaction; on local failure compensate by deleting the Keycloak user. Every admin action writes a `user_admin_audits` row (dedicated table; the generic audit log stays Later UC-H15). `Idempotency-Key` on create. Gated by new module `user_management` (licensed via `MODULES_ENABLED`; customers on AD/Entra can switch it off and manage users in their directory). `KeycloakAdminClient` is an interface with an HTTP implementation so tests use a fake. *Rationale:* SMB customers have no IdP admin skills and want one HR screen; least-privilege service account limits blast radius; Keycloak-first + compensation avoids orphan local rows, and login-time sync repairs any drift. (2026-11-19, architect) *Partly superseded by D-29 (actor role `admin`, allow-list, `LAST_ADMIN`), D-32 (no local fallback) and D-34 (module default for directory realms).*
- **D-23 — Redis 7 for sessions, cache, atomic locks, rate limiting and queue (supersedes D-03).** `phpredis` extension (no `predis` dep). Separate logical DBs so `cache:clear` never drops sessions or jobs: `default` 0, `cache` 1 (cache, locks, rate limiters, JWKS, Keycloak admin token, idempotency keys), `session` 2, queue 3; prefix `lms-`. `failed_jobs` stays in Postgres; the `jobs`/`cache`/`sessions` tables are kept only as a fallback driver. Managed/TLS Redis via `REDIS_SCHEME=tls` / `REDIS_URL`. *Rationale:* horizontal scaling (user requirement) needs fast shared session/lock/throttle state; DB-backed locks and queue polling add load on the primary DB. (2026-11-19, architect)
- **D-24 — Horizontal scaling is first-class; RustFS as dev S3 (amends D-15).** `nginx`, `app`, `worker`, `keycloak` run as N replicas behind a load balancer with **no sticky sessions**. All state is in Postgres, Redis or the S3 disk. Every scheduled task uses `onOneServer()` + `withoutOverlapping()`. Migrations run as a one-off job before rollout, never in the entrypoint. `/readyz` checks Postgres + Redis only. Branding/uploads go to `BRANDING_DISK=s3`: **RustFS** (S3-compatible) in dev/compose with an idempotent `s3-init` container that creates the bucket; prod may use any S3-compatible store via `AWS_ENDPOINT`. The `branding` local disk is only for single-node installs. *Rationale:* enterprise customers need HA and rolling deploys; dev uses the same S3 code path as prod (12-factor X). (2026-11-19, architect)
- **D-25 — CI pipeline (amends D-10).** Jobs: `lint` (Pint), `openapi` (Redocly lint of `docs/api/openapi.yaml`), `unit`, `feature` (services Postgres 17 + Redis 7, responses validated against the spec), `smoke` (`docker compose up --wait`, migrate+seed, curl `/healthz` `/readyz` and Keycloak discovery), `package` (after all others; push only). Images `ghcr.io/${{ github.repository }}/{app,nginx}` lowercased = `ghcr.io/heyadityak/lms/{app,nginx}`; `linux/amd64` on `main`, `linux/amd64,linux/arm64` on `v*` tags (QEMU). *Rationale:* fast feedback on PRs, real-container confidence before publishing, ARM customers served by release tags without slowing every main build. (2026-11-19, architect)
- **D-26 — Configurable leave-year start (amends D-04).** `LEAVE_YEAR_START_MONTH` (1–12, default 1 = calendar year) sets the first month of the leave year; a leave year is labelled by the calendar year it starts in (`2026` with start month 4 = 2026-04-01…2027-03-31). Requests may not span leave years. The accrual job runs on day 1 of that month at 00:10 (`APP_TIMEZONE`). Proration counts months remaining from the joining month to the year end. Per deployment only (env), not admin-editable. Changing it on a live deployment needs a planned migration of open balances (out of scope). *Rationale:* answers open question 1 (fiscal years such as April–March are common, e.g. India) without changing the ledger model. (2026-11-19, architect)
- **D-27 — FrankenPHP + Laravel Octane instead of PHP-FPM (amends D-09; supersedes every php-fpm/FastCGI detail).** App image `FROM dunglas/frankenphp:<pinned 1.x>-php8.4-alpine` (exact tag pinned, e.g. `1.9.1-php8.4-alpine`), extensions via `install-php-extensions pdo_pgsql redis intl zip opcache pcntl bcmath`. Web process: `php artisan octane:frankenphp --host=0.0.0.0 --port=8000 --workers=${OCTANE_WORKERS} --max-requests=${OCTANE_MAX_REQUESTS}` (`OCTANE_SERVER=frankenphp`, worker mode). `APP_SERVER_MODE=classic` falls back to non-worker FrankenPHP (`frankenphp php-server --listen :8000 --root public/`) for debugging. FrankenPHP's automatic HTTPS is off (`SERVER_NAME=:8000`); NGINX stays the edge reverse proxy/load balancer in front of N app replicas (`proxy_pass http://$APP_UPSTREAM`, no FastCGI), terminates TLS in prod (or the platform LB does), serves static assets and sets security headers. `worker`, `scheduler` and one-off jobs use the same image with artisan CLI commands. `/healthz` `/readyz` are served by Octane; container `HEALTHCHECK` curls `:8000/healthz`. Octane handles SIGTERM gracefully. Worker-mode safety rules are in AGENTS.md §4. Caddy 103 Early Hints and Mercure are available but **not enabled** (Later). New composer dep: `laravel/octane`. Images: `ghcr.io/heyadityak/lms/app` (FrankenPHP) and `ghcr.io/heyadityak/lms/nginx`. *Rationale:* user requirement; worker mode removes per-request framework boot (lower latency, fewer replicas), the app binds HTTP itself (12-factor VII), and one binary replaces php-fpm + FastCGI config. (2026-11-19, architect)
- **D-28 — GitHub wiki is a generated mirror of `docs/`.** `scripts/docs-to-wiki.sh` (bash + embedded Python 3, stdlib only) flattens `docs/**/*.md` + `AGENTS.md` into Title-Case wiki pages, rewrites relative `.md` links to page names, other repo files to `github.com/heyadityak/lms/blob/main/…` (images to `raw.githubusercontent.com`), leaves fenced/mermaid blocks untouched, and regenerates `Home`, `_Sidebar`, `_Footer`. `.github/workflows/wiki.yml` runs it on push to `main` (docs paths) + `workflow_dispatch`, commits as `github-actions[bot]` only on change and pushes `HEAD` (wiki default branch is `master`). Wiki edits are overwritten. *Rationale:* one source of truth reviewed via PRs; the wiki gives readable navigation without a docs site. (2026-11-19, platform)
- **D-29 — Separate additive `admin` realm role (supersedes D-18; partly supersedes D-22).** New realm role `admin` owns branding (UC-B1–B6), modules and in-app Keycloak user management (UC-U1–U7). `hr_admin` keeps HR operations: departments, leave types, holidays, working week, balance adjustments, reports, users' HR attributes (department, manager, joining date, codes, deactivation), and remains the approval fallback. Every user still has exactly one **base** role (`hr_admin` > `manager` > `employee`, highest wins, none ⇒ login refused); `admin` is **additive**, mirrored to new column `users.is_admin` (`users.role` keeps the base role; `Role` enum gains `Admin`). Assignment allow-list `employee|manager|hr_admin|admin` (`PUT /admin/users/{id}/roles` = one base role + optional `admin`). Guardrails: G1 only `admin` uses UC-U*; G2 no change to your own roles and no self-disable (403 `SELF_MODIFICATION_FORBIDDEN`); G3 the last active `admin` cannot lose `admin` or be disabled (409 `LAST_ADMIN`, replaces `LAST_HR_ADMIN`; Redis lock `lock:admin-guard`). OpenAPI `x-roles: [admin]` on `/admin/users*`, branding writes and `/modules`. Dev realm adds user `dave` (employee + admin). *Rationale:* user answer to open question 3 (IT vs HR split). Additive rather than a fourth exclusive rank so a small customer can give one person `hr_admin` + `admin`, and an IT admin can still apply for leave without HR rights. (2026-11-19, architect)
- **D-30 — Weekend days admin-editable (amends D-14 settings list).** `LMS_WEEKEND_DAYS` stays the env default; setting `work.weekend_days` overrides it (same `effective = DB ?? env` pattern as branding). Edited by `hr_admin` (UC-H16; HR policy like holidays) via `/admin/settings/working-week` and `GET/PATCH /api/v1/settings/working-week` (GET any role; `null` resets). Validation: ISO weekdays 1–7, unique, ≤ 6 items (at least one working day). `WorkingDayCalculator::forRange` reads it at submit/approve time; `days` of already-submitted (pending or approved) requests is **never** recalculated, same as holidays. *Rationale:* user answer to open question 4; customers with Fri/Sat or six-day weeks self-serve without a redeploy. (2026-11-19, architect)
- **D-31 — SL backdate default of 7 days confirmed.** `LMS_SL_MAX_BACKDATE_DAYS=7` seeds SL `max_backdate_days`; other seeded types stay 0. *Rationale:* user answer to open question 5; HR can change it per leave type (UC-H3). (2026-11-19, architect)
- **D-32 — Identity admin is blocked when Keycloak is unavailable.** Every `/admin/users` API operation and the web identity-user pages, **including list and detail**, return 503 `IDP_UNAVAILABLE` (with `Retry-After`) when the Admin API is unreachable, times out or returns 5xx. No stale read-only list from the local mirror. HR pages and `/api/v1/users` that read only local data keep working. *Rationale:* user answer to open question 8; a stale list could show wrong enabled/role state and invite wrong decisions. (2026-11-19, architect)
- **D-33 — No LMS-published Keycloak image or login theme.** Customers run upstream `quay.io/keycloak/keycloak:26.x` (prod `start`; clustered `ispn` cache is the default) and import/configure the documented realm (`docker/keycloak/realm-lms.json` is the dev import and the reference). Nothing Keycloak-related is built or pushed by CI; `docker/keycloak/Dockerfile` is to be removed (platform). Login page branding (UC-B9) is the customer's own Keycloak configuration. *Rationale:* user answer to open question 7; fewer artefacts to patch for Keycloak CVEs, customers often already run Keycloak. (2026-11-19, architect)
- **D-34 — `user_management` off for directory-backed realms, by checklist.** Deployment checklist: for realms backed by LDAP/AD federation or Entra ID / SAML brokering, leave `user_management` out of `MODULES_ENABLED`. `.env.example` keeps it listed with a comment saying so. No auto-detection of federation. *Rationale:* user answer to open question 9; simplest option, the operator knows the customer's directory at deploy time. (2026-11-19, architect)

- **D-37 — Phase-1 container details (amends D-27, SYSTEM_DESIGN §3).** (a) No separate `vendor` stage: `app-prod` runs `composer install --no-dev -o` itself with the composer binary bind-mounted from `composer:2` (`RUN --mount`), so platform checks run against the real PHP 8.4 + extensions and no composer binary ships. - **D-38 — CI split into `ci.yml` + `package.yml` (amends D-25).** `ci.yml` (`lint`, `openapi`, `unit`, `feature`; PR, push `main`, dispatch, `workflow_call`; superseded PR runs cancelled). `package.yml` (push `main`, tags `v*`, dispatch) runs `ci` (reusable `workflow_call` of `ci.yml`) → `smoke` → `push` (matrix app/nginx). `workflow_call` chosen over `workflow_run`: `workflow_run` runs in the default-branch context, so tags would need `head_sha`/`head_branch` plumbing and metadata-action would not see the tag ref; `workflow_call` keeps the real push ref (semver tags work natively) and gates on success through `needs`. Cost: on a push to `main`, CI runs twice (standalone `CI` + inside `package`). Smoke therefore runs on `main`/tags only, not on PRs. Smoke runs `migrate` without `--seed` until `DemoSeeder` exists (phase 5). Redocly via `npx @redocly/cli@2.80.0` (pinned). Tags: `sha`, branch, semver `{{version}}` + `{{major}}.{{minor}}`, `latest` on default branch only (`flavor: latest=false`). (2026-11-19, platform)
- **D-39 — Phase-3 Keycloak auth details (amends D-20, D-22, SYSTEM_DESIGN §5/§10.1).** (a) Guard name stays `keycloak-jwt` (`auth:keycloak-jwt`) as in AGENTS/SYSTEM_DESIGN; the draft's `auth:keycloak` was renamed. Middleware aliases: `role:<base,...>` (users.role) and `admin` (users.is_admin). (b) The web callback provisions from the **access token** returned by the code exchange, verified by the same `KeycloakJwtGuard::decode()` (JWKS, RS256, iss, aud/azp, exp/nbf); Socialite's userinfo payload is not trusted for roles. The guard accepts only `typ=Bearer` tokens with `exp`, pins `alg=RS256` before key lookup (rejects `none`/HS*), and ignores `use=enc` keys. (c) Unknown `kid` → one refetch guarded by Redis lock `keycloak:jwks-refresh`, held 10 s and never released (= rate limit across replicas). (d) Provisioning: by `keycloak_sub`, else by email **only if `email_verified`** (links a pre-created user or re-links a stale sub after a user/realm is re-created in Keycloak, logged `auth.user_relinked`); an unverified email that collides with a local user → 403. No base role (incl. `admin` alone) → 403 (web + API); inactive user → web 403, API 401. (e) Realm import: `default-roles-lms` defined explicitly with `employee` (Keycloak ignores `defaultRole.composites` on import); roles mapper writes `realm_access.roles` to access + ID token + userinfo; `lms-dev-cli` (DEV ONLY, direct grant) gets an audience mapper for `lms-api-cli`; `lms-admin` default client scopes `basic` + built-in `kc-admin-api` (Keycloak 26.8 Admin API rejects tokens without the admin audience: "Expected audience not available"), no realm roles; effective realm-management roles are manage/view/query-users plus `query-groups` (composite of `view-users`). (f) users: the stock create migration is restored (minus `password_reset_tokens`); phase-3 columns come in `2026_11_19_000000_add_keycloak_columns_to_users_table` (`keycloak_sub` nullable unique, `role` + CHECK, `is_admin`, `is_active`, drop `password`); `last_login_at`, `public_id` and the rest stay for domain. (g) `JWT::$leeway` is a php-jwt static; it is set from config on every decode (constant value, no request state). (2026-11-19, platform)
- **D-40 — Phase-4 API plumbing details (amends D-21, API_GUIDELINES §4/§7/§8).** (a) Problem `code`s are UPPERCASE from the spec's `ProblemCode` enum; `type` = `urn:lms:problem:<code lowercased, _→->`. The enum has no `METHOD_NOT_ALLOWED` or generic `CONFLICT`, so framework 405 → `BAD_REQUEST` (status stays 405, `Allow` header kept), a bare `abort(409)` → `INVALID_TRANSITION`, other unmapped 4xx → `BAD_REQUEST`, 5xx → `INTERNAL_ERROR` (503 → `SERVICE_UNAVAILABLE`). **Architect:** add `METHOD_NOT_ALLOWED` to the enum if a dedicated code is wanted. (b) 500 bodies never carry `detail`/trace, even with `APP_DEBUG=true` (spec wins over the phase-4 brief). (c) `WWW-Authenticate: Bearer error="invalid_token"` only when a token was sent; plain `Bearer` without one (RFC 6750 §3.1). (d) JWKS unreachable with no cached copy → 503 `SERVICE_UNAVAILABLE` + `Retry-After: 30` (guard used to answer 401). (e) `EnsureIdempotency` follows the spec, not the brief: slot `idem:{user id}:{sha256(key)}` (no route in the key; method + path are part of the fingerprint, so reusing a key on another endpoint is 422 `IDEMPOTENCY_KEY_REUSED`), stores 2xx and 422 only (other 4xx and 5xx release the key), key 8–255 visible ASCII else 422 `VALIDATION_FAILED`; processing marker TTL 60 s (a crashed worker cannot block a key for 24 h), result TTL 24 h; replays all headers except `Date`/cookies. User id is the bigint until domain adds `public_id` (Redis-internal, never exposed). (f) `throttle` uses the cache `RateLimiter` (Redis cache store DB 1 in every deployment) instead of `throttleWithRedis()`: same headers, but tests run on the `array` store so counters cannot leak between test runs (the Redis variant made the `login` limiter fail reruns within a minute). (g) `EnsureModuleEnabled` is prepended to the middleware priority list before `AuthenticatesRequests`; otherwise Laravel's priority sort ran auth first and a disabled module answered 401 instead of 404. (h) Octane log passthrough: the entrypoint passes `--log-level=${CADDY_LOG_LEVEL:-WARN}`, which makes `octane:frankenphp` write every worker stderr line raw (app Monolog JSON and Caddy JSON) instead of re-parsing for `msg` ("unknown error"); chosen over a `msg`-emitting formatter because Octane drops `level: info` lines and reformats the rest as text. (i) `/api/docs` uses Redoc 2.5.0 from jsDelivr with SRI sha384 (3.x exists; 2.x kept for its stable `<redoc spec-url>` API). (2026-11-19, platform)
