# Decisions (ADR-lite)

Format: **D-NN — Title.** Decision. *Rationale.* (date, author). Append-only. To supersede an entry, add a new one and mark the old one "Superseded by D-xx".

- **D-01 — Single-tenant, one deployment per customer.** One DB per customer, no `tenant_id` columns. *Rationale:* white-label SMB/enterprise delivery. Isolation by infrastructure is simpler and safer than row-level multitenancy. (2026-11-19, architect)
- **D-02 — Ledger-based balances.** Append-only `leave_ledger_entries`, balance = SUM. No mutable balance columns. *Rationale:* auditability, idempotent accrual, and it fixes the original's lost-update/no-history design. Data volume is small, so SUM is fast with the `(user_id, leave_type_id, year)` index. (2026-11-19, architect)
- **D-03 — `database` driver for queue, cache, session.** No Redis. *Rationale:* minimal backing services (user requirement). Postgres handles the load of an LMS. Stateless processes are preserved. (2026-11-19, architect) *Superseded by D-23.*
- **D-04 — Calendar leave year, yearly grant on Jan 1.** No monthly accrual and no anniversary-based accrual in MVP. Requests may not span years. *Rationale:* simplest correct model. The original's anniversary-on-login update was not idempotent. Monthly accrual is Later (UC-H13). (2026-11-19, architect) *Amended by D-26 (configurable leave-year start month).*
- **D-05 — No Node/Vite build.** Blade + one hand-written CSS file driven by CSS custom properties. Auth screens written by hand (Laravel 12 starter kits require React/Vue/Livewire + Node). *Rationale:* fewer toolchains in the image and CI. Theming only needs CSS variables. (2026-11-19, architect)
- **D-06 — Overlap enforced twice:** app check + Postgres `EXCLUDE USING gist` on `daterange` for pending/approved. *Rationale:* race-proof without app locks alone. Needs `btree_gist`, which ships with the postgres image. (2026-11-19, architect)
- **D-07 — No `draft` status; `taken` is derived.** Statuses: pending, approved, rejected, cancelled. *Rationale:* drafts add UI/state without user value for a form this small. "Taken" = approved and started, computable. (2026-11-19, architect)
- **D-08 — Single-level approval in MVP.** Approver = active direct manager, else any HR admin. Nobody approves their own request. Multi-level and delegation are reserved module keys (`available=false`). *Rationale:* covers the original (HOD approves) and most SMBs. Approver is resolved at action time, so reorgs don't strand requests. (2026-11-19, architect)
- **D-09 — One multi-stage Dockerfile, two published images** (`app` from `app-prod`, `nginx`). The app image also runs worker, scheduler and one-off commands. Caches are built at container start, not build time. *Rationale:* 12-factor build/release/run. One artefact per role. Config is unknown at build time. (2026-11-19, architect)
- **D-10 — CI tests use `setup-php` + Postgres 17 service, not the Docker image.** *Rationale:* faster, cached. Parity is kept on PHP minor + Postgres major. The image is still built (and fails the pipeline if broken) in `package`. (2026-11-19, architect) *Amended by D-25 (Redis service, OpenAPI lint, smoke test, multi-arch).*
- **D-11 — PHPUnit (not Pest), two suites.** Unit = plain `PHPUnit\Framework\TestCase`, no DB. Feature = Postgres `lms_test`. Never SQLite. *Rationale:* user choice. Postgres-only DDL must be exercised. (2026-11-19, architect)
- **D-12 — Users are never hard-deleted.** Deactivate instead. *Rationale:* audit/history. The original lost leave history when deleting employees. (2026-11-19, architect)
- **D-13 — Global leave-type quotas (no per-department override in MVP).** *Rationale:* the original set quotas per HOD/department. Overrides are Later (UC-H10) via an extra policy table without changing the ledger. (2026-11-19, architect)
- **D-14 — White-label config: env = defaults + licensed ceiling, `settings` table = admin overrides.** `effective = DB override ?? env default`. For modules: `enabled = licensed (MODULES_ENABLED env) ∧ available (registry) ∧ ¬disabled (settings)`, so an admin can switch off a licensed module but never switch on an unlicensed one. *Rationale:* 12-factor config per deployment, with the vendor controlling licensing at deploy time. Customers self-serve within it. Settings are data (in the DB), not config. (2026-11-19, architect)
- **D-15 — Branding assets on a Laravel disk (`BRANDING_DISK`), served through `/branding/{asset}`.** Local volume in dev, S3-compatible in prod. Never baked into the image. Content-hashed filenames. No SVG. *Rationale:* stateless containers. One code path for local and S3. Avoids SVG stored-XSS. (2026-11-19, architect) *Amended by D-24 (S3 disk everywhere incl. dev via RustFS; local disk only single-node).*
- **D-16 — Theming = CSS custom properties injected from validated hex settings.** No per-customer CSS builds and no arbitrary custom CSS in MVP. *Rationale:* zero build step, no injection surface. (2026-11-19, architect)
- **D-17 — Disabled module ⇒ 404 (not 403), hidden in UI, and inert in domain** (e.g. holidays off ⇒ holidays not excluded from day counts). *Rationale:* the feature appears absent rather than forbidden. Domain behaviour stays consistent with what the user can see. (2026-11-19, architect)
- **D-18 — Branding/modules administered by `hr_admin`; no separate customer-admin role in MVP.** *Rationale:* keeps 3 roles. Revisit if enterprises need IT-admin separation (open question). (2026-11-19, architect)
- **D-19 — Sandwich rule off.** Weekends/holidays never count. *Rationale:* illegal or unpopular in many jurisdictions. Per-type flag is Later. (2026-11-19, architect)
- **D-20 — Keycloak 26 is the identity provider and RBAC authority; Sanctum removed.** One Keycloak per deployment (own container, own `keycloak` database on the same Postgres server, clustered in prod). Realm `lms`, realm roles `employee|manager|hr_admin`. Clients `lms-web` (confidential, OIDC auth code, used by Laravel Socialite + `socialiteproviders/keycloak`) and `lms-api-cli` (public, auth code + PKCE). Web: first login provisions the user by `users.keycloak_sub` (unique), every login syncs realm roles into `users.role` (a cache; Keycloak wins), session in Redis, logout is RP-initiated. API: Bearer JWT (RS256) validated by a custom guard against the realm JWKS cached in Redis, checking `iss`, `aud`/`azp` (allow-list `KEYCLOAK_ALLOWED_AUDIENCES`), `exp`/`nbf`. Removed from the app: passwords, `password_reset_tokens`, `personal_access_tokens`, forgot/reset/change password, account-created mail, token issue endpoints. HR still manages department, manager, joining date and deactivation in the app; roles are assigned in Keycloak only. Resource-level authorization (e.g. only the direct manager approves) stays in Laravel Policies. New composer deps: `laravel/socialite`, `socialiteproviders/keycloak`, `firebase/php-jwt`; drop `laravel/sanctum`. *Rationale:* enterprise customers federate their own directory (LDAP/AD, SAML, Entra ID) and get MFA/SSO/brute-force protection without app code; the Keycloak login theme can be white-labelled per customer. Policies keep the business rules that Keycloak roles cannot express. (2026-11-19, architect) *Partly superseded by D-22: the app may now create users and assign roles through the Keycloak Admin API; Keycloak remains the source of truth.*
- **D-21 — Contract-first REST API.** `docs/api/openapi.yaml` (OpenAPI 3.1) is the source of truth; guidelines in `docs/API_GUIDELINES.md`. URI versioning `/api/v1`, plural kebab-case nouns, state transitions as `POST …/{id}/approve|reject|cancel`, `/me` for the caller. Envelope `{data, meta, links}` via API Resources, snake_case, ISO-8601, public ids are ULIDs in a `public_id` column (bigint `id` never exposed). Errors are RFC 9457 `application/problem+json` with a stable `code`. Pagination `page[number]`/`page[size]` (max 100), `filter[...]`, `sort=`, `include=`. `Idempotency-Key` on `POST /leave-requests` (Redis, 24 h, replays the first response). `X-RateLimit-*` / `Retry-After` from Redis limiters. Every `/api/v1` route is behind the `api` module (404 when off). QA validates every API feature-test response against the spec (`osteel/openapi-httpfoundation-testing`, dev dep). Docs UI at `/api/docs` when `api` is enabled. *Rationale:* lets domain, QA and API consumers work in parallel against one contract; predictable machine-readable errors; safe client retries on flaky mobile networks. (2026-11-19, architect)
- **D-22 — In-app user administration through the Keycloak Admin REST API (supersedes D-20's "app never edits roles").** Keycloak stays the source of truth for identity and roles; the LMS writes to it, then mirrors locally. Auth: confidential service-account client `lms-admin` (client-credentials), service-account roles `realm-management`: `manage-users`, `view-users`, `query-users` only (never `realm-admin`); token cached in Redis until 30 s before expiry. Only `hr_admin` (a split-off `admin` role is a Later option). Operations: list/search, create (no password; `execute-actions-email` `UPDATE_PASSWORD`+`VERIFY_EMAIL`), update profile, enable/disable (disable also calls `logout` for the user), password-reset email, assign/revoke realm roles limited to the allow-list `employee|manager|hr_admin`; LMS attributes (department, manager, joining date) edited in the same form. Guardrails: no self-demotion/self-disable; last active `hr_admin` cannot be demoted/disabled (checked under a Redis lock); federated users (`federationLink` set, LDAP/AD) are read-only for profile fields, roles editable only if the provider accepts it. Keycloak 409 → `IDP_CONFLICT` (409), Keycloak unreachable/5xx → `IDP_UNAVAILABLE` (503), federated write → `IDP_READ_ONLY` (422). Consistency: Keycloak first (get id), then local insert with pre-provisioned `keycloak_sub` in a DB transaction; on local failure compensate by deleting the Keycloak user. Every admin action writes a `user_admin_audits` row (dedicated table; the generic audit log stays Later UC-H15). `Idempotency-Key` on create. Gated by new module `user_management` (licensed via `MODULES_ENABLED`; customers on AD/Entra can switch it off and manage users in their directory). `KeycloakAdminClient` is an interface with an HTTP implementation so tests use a fake. *Rationale:* SMB customers have no IdP admin skills and want one HR screen; least-privilege service account limits blast radius; Keycloak-first + compensation avoids orphan local rows, and login-time sync repairs any drift. (2026-11-19, architect)
- **D-23 — Redis 7 for sessions, cache, atomic locks, rate limiting and queue (supersedes D-03).** `phpredis` extension (no `predis` dep). Separate logical DBs so `cache:clear` never drops sessions or jobs: `default` 0, `cache` 1 (cache, locks, rate limiters, JWKS, Keycloak admin token, idempotency keys), `session` 2, queue 3; prefix `lms-`. `failed_jobs` stays in Postgres; the `jobs`/`cache`/`sessions` tables are kept only as a fallback driver. Managed/TLS Redis via `REDIS_SCHEME=tls` / `REDIS_URL`. *Rationale:* horizontal scaling (user requirement) needs fast shared session/lock/throttle state; DB-backed locks and queue polling add load on the primary DB. (2026-11-19, architect)
- **D-24 — Horizontal scaling is first-class; RustFS as dev S3 (amends D-15).** `nginx`, `app`, `worker`, `keycloak` run as N replicas behind a load balancer with **no sticky sessions**. All state is in Postgres, Redis or the S3 disk. Every scheduled task uses `onOneServer()` + `withoutOverlapping()`. Migrations run as a one-off job before rollout, never in the entrypoint. `/readyz` checks Postgres + Redis only. Branding/uploads go to `BRANDING_DISK=s3`: **RustFS** (S3-compatible) in dev/compose with an idempotent `s3-init` container that creates the bucket; prod may use any S3-compatible store via `AWS_ENDPOINT`. The `branding` local disk is only for single-node installs. *Rationale:* enterprise customers need HA and rolling deploys; dev uses the same S3 code path as prod (12-factor X). (2026-11-19, architect)
- **D-25 — CI pipeline (amends D-10).** Jobs: `lint` (Pint), `openapi` (Redocly lint of `docs/api/openapi.yaml`), `unit`, `feature` (services Postgres 17 + Redis 7, responses validated against the spec), `smoke` (`docker compose up --wait`, migrate+seed, curl `/healthz` `/readyz` and Keycloak discovery), `package` (after all others; push only). Images `ghcr.io/${{ github.repository }}/{app,nginx}` lowercased = `ghcr.io/heyadityak/lms/{app,nginx}`; `linux/amd64` on `main`, `linux/amd64,linux/arm64` on `v*` tags (QEMU). *Rationale:* fast feedback on PRs, real-container confidence before publishing, ARM customers served by release tags without slowing every main build. (2026-11-19, architect)
- **D-26 — Configurable leave-year start (amends D-04).** `LEAVE_YEAR_START_MONTH` (1–12, default 1 = calendar year) sets the first month of the leave year; a leave year is labelled by the calendar year it starts in (`2026` with start month 4 = 2026-04-01…2027-03-31). Requests may not span leave years. The accrual job runs on day 1 of that month at 00:10 (`APP_TIMEZONE`). Proration counts months remaining from the joining month to the year end. Per deployment only (env), not admin-editable. Changing it on a live deployment needs a planned migration of open balances (out of scope). *Rationale:* answers open question 1 (fiscal years such as April–March are common, e.g. India) without changing the ledger model. (2026-11-19, architect)
